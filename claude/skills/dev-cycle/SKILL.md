# 开发全流程（Claude 指挥，Reasonix 执行）

你是大脑，Reasonix 是手。分工固定，不许调换：

| 阶段 | 谁做 | 为什么 |
|---|---|---|
| 0 铺路 | 你 | 头一次在这个项目跑要先配好，否则无头调用会卡死 |
| 1 摸底 | 你（大海捞针可派 `explore` 定位） | 要判断这事碰到哪些锁定决策，得有全局上下文 |
| 2 设计审查 | **你，亲自做，不许外派** | 这是整条流程存在的理由 |
| 3 实现 | Reasonix `implementer` | 方案定死之后是执行题 |
| 4 验证 | Reasonix `verifier` | 跑命令贴结果，机械活 |
| 5 验收 | 你 | 换了个模型在干活，更不能只看它自己怎么说 |
| 6 汇报 | 你 | 说人话 |

## 怎么调 Reasonix

```bash
python ~/.claude/scripts/rx.py doctor                    # 自检，不花钱
python ~/.claude/scripts/rx.py sub explore     --max-chars 3000 - < 定位任务文件
python ~/.claude/scripts/rx.py sub implementer --model deepseek/deepseek-v4-pro --max-chars 6000 - < 任务文件
python ~/.claude/scripts/rx.py sub verifier    - < 任务文件
```

**任务一律写进文件再用 `-` 从 stdin 传。** 任务文本又长又带中文引号和换行，
塞进命令行必然被转义搞坏。临时文件写到系统临时目录，别脏了仓库。

开关：`--model`、`--max-chars N`（裁回流正文，0=不裁）、`--max-steps N`（卡轮数防跑飞）、
`--dir PATH`（默认从当前目录往上找项目根）、`--timeout SEC`（默认 1800）。

### 成本纪律：省的是你这边，不是 Reasonix 那边

Reasonix 跑 deepseek 档（¥1~¥3 每 M 输入），一次调用的 ~24k 系统提示合几分钱。
**贵的是你的上下文**——子代理返回的每个字都进你这里，还会在后续每轮重发。所以：

- **按独立性拆活，不要为了省调用次数硬合并。** 合并只省 Reasonix 那几分钱，
  代价是几件事的证据混在一起、返回更长、其中一件出问题时打回的任务文件还得
  把三件事的上下文重写一遍。**但互相耦合的必须合在一起派**——B 依赖 A 定下来的
  接口形状时拆开会拿到两套不一致的实现，那才是真烧钱。
- **implementer 用 `--model deepseek/deepseek-v4-pro`。** 比默认的 flash 档每次贵约
  ¥0.05，但 flash 写崩一次就要多一整轮打回——你重新审缺口、重写任务文件、再验收一遍，
  那一轮的代价比这 ¥0.05 高两个数量级。
- **implementer 用 `--max-chars 6000`、explore 用 `--max-chars 3000` 裁回流正文**，
  被裁的部分落到临时文件，`[rx]` 那行会给路径，需要细看时再去读。
  explore 用默认的 flash 档就行，它只是定位，不做判断。
- **verifier 不要设 `--max-chars`。** 它的返回本来就是压缩过的（一张表加 FAIL 原文），
  而那些原文正是你验收要吃的证据，裁掉就等于白跑。

### Reasonix 看不见你的对话

它是另一个进程、另一个模型，**只能看到你写进任务文件的东西**。每个任务文件必须自带：
要改什么、改到什么程度算完成、第 2 步得出的约束和红线（逐条抄，不要写"按之前说的办"）、
相关文件路径、以及明确的"不要 git commit"。

## 0. 铺路（每个项目只做一次）

先跑 `rx.py doctor`。看两件事：

- **`providers` 是空的** → 密钥没配。让用户自己跑 `reasonix setup`，你不碰密钥。
- **`config` 不是 `reasonix.toml`，或 `perm` 的 `allow_rules` 是 0** → 这个项目还没铺过。

没铺过就先铺：从项目里认出门禁命令（指令文件 > `package.json` scripts > `Makefile` >
`pyproject.toml` > CI 配置），在项目根写一份 `reasonix.toml`：

```toml
[permissions]
mode = "ask"          # 兜底仍然要问，放行的只有下面列出的
allow = [
    # 这个项目的门禁命令，一条一条列
    # 只读 git：status / diff / log / show / branch / rev-parse / ls-files
    # 提交：git add / git commit（到此为止）
]
deny = [
    'Bash(rm -rf*)',
    'Bash(git clean*)',
    'Bash(git push*)',
]
```

**Windows 上两种斜杠都要列。** Reasonix 的 bash 工具走 Git Bash，
`.venv\Scripts\python.exe` 这种反斜杠路径会被 shell 吞掉，实际执行的是正斜杠形式；
只写文档里那种反斜杠写法会匹配不上。

写完把 `reasonix.toml` 给用户看一眼再往下走——这是在给另一个 AI 开权限，值得他扫一眼。

**第 1 步的 `explore` 不受这一步阻塞**：它是只读子代理，在没铺过 `reasonix.toml`
的项目里也能跑通（实测过）。要铺路的是会写文件、会跑门禁的 `implementer` 和 `verifier`。

## 1. 摸底

读项目的指令文件（`AGENTS.md` / `CLAUDE.md` / `CONTRIBUTING.md`，取第一个存在的）、
它点名要读的其他文档、`git status --short --branch` 和最近几条提交、任务涉及的现有代码。

**指令文件和 git 状态必须你自己读**，那是宪法和现场，不外派。

项目自带的专用技能能覆盖这个任务，**先用那个技能**，它比临场推准。

### 大海捞针可以外派给 explore

不知道该动哪些文件、要在大仓里横扫时，把**定位**派出去：

```bash
python ~/.claude/scripts/rx.py sub explore --max-chars 3000 - < 定位任务文件
```

`explore` 是 Reasonix 的 builtin 只读子代理。任务文件里明确要它**返回文件路径清单
（`路径:行号` + 一句话说明为什么相关），不要返回结论、不要给修改建议**。

**什么时候不派**：已经知道改动就在一两个文件里的小活。派一次的往返时间比你直接
Glob/Grep 长得多，省不出东西来。只有"这事牵扯到哪些地方我完全没数"时才值得。

**三条不能破的边界**：

1. **explore 的返回是线索，不是证据。** 拿到清单后**你自己去读那些文件的原文**。
   第 2 步的影响面和红线检查只能吃你亲眼读过的代码，不能吃它的摘要——
   它是便宜档模型，不会漏掉你点名要找的东西，但会漏掉**你不知道该找的东西**：
   那个没人预料到的耦合、那句 `// 别动这里，见 BUG-1234` 的注释。
2. **它说"没有别的相关文件"不算数。** 那可能只是它没找到。按清单读完之后，
   如果代码里引用了清单之外的东西，自己补搜。
3. **它给的任何方案倾向一律忽略。** 设计审查是第 2 步的事，不接受外部输入。

## 2. 设计审查（你亲自做）

不派子代理，不外包，就是你自己想。产出六项，写进回复里：

1. **真正要解决的问题**——用户说的和实际要改的往往不是一回事。
2. **影响面**——动到哪些模块、哪些边界、有没有协议或接口变更。
3. **红线检查**——把项目指令文件里的硬约束逐条过一遍。没有指令文件时至少过这几条：
   凭据会不会进 Git / 日志？有没有对外暴露端口或放宽认证？有没有依赖某个具体实现
   而不是抽象边界？用户可见文案有没有内部黑话？涉不涉及不可恢复的删除？
4. **方案 + 至少一个被否掉的替代方案**，写清为什么否。
5. **验证矩阵**——改完要跑哪些门禁才算数。
6. **任务拆分**——拆成能独立交给 `implementer` 的条目。**按独立性拆，不按大小拆**：
   互不依赖的分开派（返回更聚焦、打回时只需重写那一件的上下文），
   B 依赖 A 定下来的接口形状的必须合并派（拆开会拿到两套不一致的实现）。

**红线冲突时停下来问用户。** 这是整条流程里唯一允许中断的地方。方案取舍你自己定。

## 3. 实现（派 implementer）

把任务写成自带上下文的任务文件派出去。权限边界由 `reasonix.toml` 兜着。

```bash
python ~/.claude/scripts/rx.py sub implementer --model deepseek/deepseek-v4-pro --max-chars 6000 - < 任务文件
```

## 4. 验证（派 verifier）

`verifier` 的 `allowed-tools` 里没有写文件的工具，改不了源码。把改动范围告诉它，
让它按范围决定跑哪些门禁。

```bash
python ~/.claude/scripts/rx.py sub verifier - < 任务文件      # 注意：不加 --max-chars
```

`implementer` 自己跑过的 lint 不算验证，那只是自查。完整验证必须由 `verifier` 独立跑。

## 5. 验收（你）

现在是另一个模型在替你干活，验收要比自己动手时更硬：

- **证据是真的吗？** 每个 PASS 有没有实际命令和输出行？只写"已执行"的当没跑。
- **无条件自己复跑一条。** 挑一条最能说明本次改动的快门禁（类型检查，或覆盖这次改动的
  那个测试），你自己用 Bash 跑一遍。**不要改成"证据可疑时才跑"**——会编证据的模型
  编出来的东西看着就是不可疑的，那正是这条要防的失败。为省上下文按退出码分流：

  ```bash
  命令 2>&1 | tail -30    # 绿的时候只留尾部；非 0 退出就重跑一次拿完整输出
  ```

  绿的时候贵不到哪去，红的时候证据一个字都不能少。
- **验证矩阵覆盖了吗？** 第 2 步列的项是不是都有结果？漏了补跑。
- **UNAVAILABLE 写清原因了吗？** 没写清就是 FAIL。
- **改动范围有没有超纲？** `git diff --stat` 扫一眼有没有顺手改的无关模块。

有 FAIL 或缺口 → 写一份**只讲具体缺口**的新任务文件打回给 `implementer`，再验一轮。
**最多来回 3 轮**；3 轮不绿就停下来，把卡住的点原原本本告诉用户，不要继续烧钱。

全绿后再提交，提交信息按项目习惯。当前在主分支就先开分支。

## 6. 汇报

只写四块，大白话，不贴堆栈不贴命令：

1. **做了什么**——从用户的角度说，不是从代码角度。
2. **验证结果**——哪些跑过了、哪些因为环境跑不了。
3. **怎么用 / 怎么看效果**——具体到点哪里、开哪个东西。
4. **需要他知道的**——遗留问题、新发现的 Bug。没有就不写。

**不要报花费。** `subagent run` 不支持 `--output-format json`，拿不到 usage 信封，
rx.py 在 `sub` 模式下报不了钱——`[rx]` 那行只有正文规模、耗时和退出码。
编一个数字出来比不报更糟。要真实账单只能走 `run` 模式，但那样会丢掉档案自带的
权限隔离（verifier 的"没有写文件工具"就是靠档案兜的），不值得换。

项目有术语表就按术语表说话，别把内部黑话漏给用户。
