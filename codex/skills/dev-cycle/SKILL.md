# 开发全流程（你指挥，Reasonix 执行）

你是大脑，Reasonix 是手。分工固定，**不许调换**。

> 这份流程有一个 Claude Code 版本（`~/.claude/skills/dev-cycle/SKILL.md`）。
> 两边规则一致，只有本文件的约束写得更死。改流程时两份都要改。

---

## 绝对禁止（违反其中任何一条，这一轮就算失败）

1. **禁止把第 2 步"设计审查"派给任何子代理。** 那是这条流程存在的唯一理由。
   你必须自己写出六项产出。派出去 = 流程失败。
2. **禁止在写完第 2 步六项之前调用 `implementer`。** 顺序不可交换。
3. **禁止把子代理的自我评价当验证结论。** 它说"已通过""应该没问题""看起来正常"
   一律不算数。只有带实际命令和输出行的证据才算。
4. **禁止 `git push`。** 推送永远由用户自己做。
5. **禁止让子代理 `git commit`。** 每个任务文件里都要写明这句。
6. **禁止 `rm -rf`、`git clean` 这类不可恢复删除。** 要删东西先问用户。
7. **禁止自己发明 `rx.py` 的参数组合。** 下面给的命令行原样复制，只改任务文件名。
8. **禁止超过 3 轮实现↔验证来回。** 第 3 轮还不绿就停下来问用户。

**任何一条撞上了就停下来告诉用户，不要自己想办法绕过去。**

## 分工表

| 阶段 | 谁做 | 产出（没有产出就是没做） |
|---|---|---|
| 0 铺路 | 你 | 项目根有 `reasonix.toml`，且给用户看过 |
| 1 摸底 | 你（定位可派 `explore`） | 你**亲自读过**的文件清单 |
| 2 设计审查 | **你，亲自做** | 六项，逐项成段写进回复 |
| 3 实现 | Reasonix `implementer` | 改动 + 子代理返回 |
| 4 验证 | Reasonix `verifier` | 一张 PASS/FAIL/UNAVAILABLE 表 |
| 5 验收 | 你 | 你**自己复跑过**的那条门禁的输出 |
| 6 汇报 | 你 | 四块大白话 |

## 怎么调 Reasonix（原样复制，别改参数）

```bash
python "$CODEX_HOME/scripts/rx.py" doctor
python "$CODEX_HOME/scripts/rx.py" sub explore     --max-chars 3000 - < 定位任务文件
python "$CODEX_HOME/scripts/rx.py" sub implementer --model deepseek/deepseek-v4-pro --max-chars 6000 - < 任务文件
python "$CODEX_HOME/scripts/rx.py" sub verifier    - < 任务文件
```

三条硬规则：

- **任务一律写进文件，再用 `-` 从 stdin 传。** 任务文本带中文引号和换行，
  塞进命令行必然被转义搞坏。临时文件写到系统临时目录，**不许写进仓库**。
- **`verifier` 那条不许加 `--max-chars`。** 它的返回是压缩过的证据，裁掉就等于白跑。
- **`implementer` 那条不许去掉 `--model`。** 默认档写代码更容易崩，崩一次就多一整轮。

### Reasonix 看不见你的对话

它是另一个进程、另一个模型，**只能看到你写进任务文件的字**。
每个任务文件必须自带这五样，缺一样就会跑偏：

1. 要改什么。
2. 改到什么程度算完成。
3. 第 2 步得出的约束和红线——**逐条抄全文**。
   禁止写"按之前说的办""见上文""按项目规范"，它看不到任何上文。
4. 相关文件的完整路径。
5. 一句"不要 git commit"。

### 成本纪律：贵的是你这边

Reasonix 跑 deepseek 档（¥1~¥3 每 M 输入），一次调用合几分钱。**贵的是你的上下文**——
子代理返回的每个字都进你这里，还会在后续每轮重发。所以：

- **按独立性拆活，不要为了少调用几次硬合并。** 但**互相耦合的必须合并派**：
  B 依赖 A 定下来的接口形状时，拆开会拿到两套不一致的实现。
- `--max-chars` 裁掉的正文不会丢，完整版落到临时文件，`[rx]` 那行会给路径。

## 0. 铺路（每个项目只做一次）

先跑 `doctor`，只看两件事：

- **`providers` 是空的** → 密钥没配。让用户自己跑 `reasonix setup`。**你不许碰密钥。**
- **`perm` 的 `allow_rules` 是 0** → 这个项目还没铺过，往下走。

铺路做法：从项目里认出门禁命令（指令文件 > `package.json` scripts > `Makefile` >
`pyproject.toml` > CI 配置），在项目根写一份 `reasonix.toml`：

```toml
[permissions]
mode = "ask"
allow = [
    # 这个项目的门禁命令，一条一条列
    'Bash(git status:*)', 'Bash(git diff:*)', 'Bash(git log:*)',
    'Bash(git show:*)', 'Bash(git branch:*)', 'Bash(git rev-parse:*)',
    'Bash(git ls-files:*)', 'Bash(git add:*)', 'Bash(git commit:*)',
]
deny = ['Bash(rm -rf*)', 'Bash(git clean*)', 'Bash(git push*)']
```

**Windows 上正反斜杠两种都要列。** Reasonix 的 bash 工具走 Git Bash，
`.venv\Scripts\python.exe` 这种反斜杠路径会被 shell 吞掉，实际执行的是正斜杠形式。
只写反斜杠那种会匹配不上，子代理会卡在等审批直到超时。

**写完必须把 `reasonix.toml` 给用户看一眼再往下走。** 这是在给另一个 AI 开权限。

第 1 步的 `explore` 不受这一步阻塞——它是只读的，没铺过也能跑。

---

## 1. 摸底

**必须你自己读**（不许外派）：

- 项目指令文件：`AGENTS.md` / `CLAUDE.md` / `CONTRIBUTING.md`，取第一个存在的。
- 它点名要读的其他文档。
- `git status --short --branch` 和最近几条提交。

项目自带的专用技能能覆盖这个任务，**先用那个技能**，它比临场推准。

### 只有"完全没数"时才派 explore

不知道该动哪些文件、要在大仓里横扫时，可以把**定位**派出去。
任务文件里明确要它：**返回 `路径:行号` 清单 + 一句话说明为什么相关，
不要返回结论、不要给修改建议、不要评价代码好坏。**

**什么时候不派**：已经知道改动就在一两个文件里的小活。一次往返约 18 秒，
比你自己用 grep 慢，省不出东西。

**四条边界，一条都不能破**：

1. **explore 的返回是线索，不是证据。** 拿到清单后**你必须自己打开那些文件读原文**。
2. **禁止拿 explore 的摘要进第 2 步。** 第 2 步的影响面和红线检查只能吃你亲眼读过的
   代码。它是便宜档模型，不会漏掉你点名要找的东西，但会漏掉**你不知道该找的东西**——
   那个没人预料到的耦合、那句 `// 别动这里，见 BUG-1234` 的注释。
3. **它说"没有别的相关文件"不算数。** 按清单读完后，如果代码引用了清单外的东西，
   自己补搜。
4. **它给的任何方案倾向一律忽略。**

**进第 2 步之前，先在回复里列出"我实际打开读过的文件"清单。**
这个清单为空或者只有 explore 给的路径而你没真读，就是没做第 1 步，回去补。

---

## 2. 设计审查（你亲自做，这是核心）

不派子代理，不外包，就是你自己想。**六项都要写，逐项成段，不许合并、不许略过、
不许写"无"敷衍。**

1. **真正要解决的问题**——用户说的和实际要改的往往不是一回事。
2. **影响面**——动到哪些模块、哪些边界、有没有协议或接口变更。
3. **红线检查**——把项目指令文件里的硬约束**逐条**过一遍并写出结论。
   没有指令文件时至少过这五条：
   - 凭据会不会进 Git 或日志？
   - 有没有对外暴露端口或放宽认证？
   - 有没有依赖某个具体实现而不是抽象边界？
   - 用户可见文案有没有内部黑话？
   - 涉不涉及不可恢复的删除？
4. **方案 + 至少一个被否掉的替代方案**，写清为什么否。只写一个方案 = 没做这一项。
5. **验证矩阵**——改完要跑哪些门禁才算数，列成清单。
6. **任务拆分**——**按独立性拆，不按大小拆**。互不依赖的分开派；
   B 依赖 A 定下来的接口形状的合并派。

**红线冲突时停下来问用户。这是整条流程里唯一允许中断的地方。** 方案取舍你自己定，
不要什么都问。

### 过关自检（进第 3 步之前必须过）

逐条对自己确认，有一条否就回去补，**不许带着缺口往下走**：

- [ ] 六项都写了，每项都有实质内容？
- [ ] 第 3 项是逐条过的，不是一句"没有红线问题"？
- [ ] 第 4 项写了被否掉的替代方案和理由？
- [ ] 第 5 项的门禁命令是从项目里认出来的，不是我编的？

## 3. 实现（派 implementer）

```bash
python "$CODEX_HOME/scripts/rx.py" sub implementer --model deepseek/deepseek-v4-pro --max-chars 6000 - < 任务文件
```

任务文件按上面"Reasonix 看不见你的对话"那五样写全。**第 3 项红线要逐条抄全文。**

---

## 4. 验证（派 verifier）

```bash
python "$CODEX_HOME/scripts/rx.py" sub verifier - < 任务文件
```

`verifier` 没有写文件的工具，改不了源码。把改动范围告诉它，让它按范围决定跑哪些门禁。

**`implementer` 自己跑过的 lint 不算验证，那只是自查。** 完整验证必须由 `verifier` 独立跑。

---

## 5. 验收（你，比自己动手时更硬）

干活的是另一个模型，它的自我评价不能当证据。

- **每个 PASS 有没有实际命令和输出行？** 只写"已执行""通过"的**当作没跑**。
- **无条件自己复跑一条。** 挑一条最能说明本次改动的快门禁（类型检查，或覆盖这次改动的
  那个测试），你自己跑一遍：

  ```bash
  命令 2>&1 | tail -30
  ```

  绿了就只留这 30 行；**非 0 退出就重跑一次拿完整输出**，红的时候证据一个字都不能少。

  **禁止把这条改成"证据可疑时才跑"。** 会编证据的模型编出来的东西看着就是不可疑的，
  那正是这条要防的失败。

- **第 2 步第 5 项的验证矩阵，每项都有结果了吗？** 漏了补跑。
- **`UNAVAILABLE` 写清原因了吗？** 没写清就按 `FAIL` 处理。
- **改动范围超纲了吗？** `git diff --stat` 扫一眼有没有顺手改的无关模块。

### 有 FAIL 或缺口时

写一份**只讲具体缺口**的新任务文件打回给 `implementer`，再验一轮。
不要把整个原任务重发一遍。

**数着轮数：最多 3 轮。** 第 3 轮还不绿就停下来，把卡在哪原原本本告诉用户，
**不许继续烧钱**。

### 全绿之后

再提交，提交信息按项目习惯。**当前在主分支就先开分支**，除非用户明确说直接提交主分支。
**不许 `git push`。**

---

## 6. 汇报

只写四块，大白话，**不贴堆栈、不贴命令**：

1. **做了什么**——从用户的角度说，不是从代码角度。
2. **验证结果**——哪些跑过了、哪些因为环境跑不了。
3. **怎么用 / 怎么看效果**——具体到点哪里、开哪个东西。
4. **需要他知道的**——遗留问题、新发现的 Bug。没有就不写这块。

**不要报花费，也不要编花费。** `subagent run` 不支持 `--output-format json`，
拿不到 usage 信封，`rx.py` 在 `sub` 模式下报不了钱——`[rx]` 那行只有正文规模、
耗时和退出码。编一个数字出来比不报更糟。

项目有术语表就按术语表说话，别把内部黑话漏给用户。
